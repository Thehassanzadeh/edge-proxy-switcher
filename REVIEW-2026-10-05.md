# Engineering review — 2026-10-05

Verdict: reasonable project structure, but not ready for a reliability sign-off.
The remaining work is a coordinated change to routing/state/authentication, not
a full UI or application rewrite. Per the requested scope, only isolated fixes
were applied. The older AUDIT.md describes a previous iteration and is not the
current list of outstanding issues.

## Follow-up — 2026-10-05 (fourth pass: round-3 lifecycle findings)

All three round-3 findings are addressed below, superseding the third-pass
retry language where noted. Verified with `tsc`, the Vitest suite (11 files /
85 tests, including the three round-3 lifecycle reproductions, which now pass
both as permanent `owner.test.ts` cases and via the provided
`/tmp/onlyproxy-review-lifecycle.test.ts` fixture: 3 passed / 15 skipped with
`-t independent`), `oxlint` (0 errors) and `vite build`, plus an isolated Edge
smoke load (fresh `--user-data-dir`, no personal settings changed). No live
proxy-traffic or two-window Edge E2E was performed. No "fully bug-free" claim
is made.

### Fixed (verified by tests/build)

- **1. Dedup lost on worker restart (High).** Applied opIds/results are now
  persisted in storage in the SAME atomic `set` as the resulting state (new
  top-level `onlyproxy:appliedOps` key, bounded at 100 entries, read
  defensively — no schema migration needed), so a resent opId dedups even on a
  fresh worker. Additionally, per the review's first fix option, `dispatchOp`
  no longer performs ANY automatic transport retry: a missing/failed response
  refreshes state and throws `BackgroundUnreachableError` reporting the
  uncertainty ("may or may not have applied — check before retrying"), so a
  lost response can never auto-execute a committed import twice. In-memory
  pending/settled dedup is retained for same-lifetime races. (This supersedes
  the third-pass "one same-opId retry" paragraph.) Regression:
  `owner.test.ts` "worker lifecycle" block (resent opId after simulated
  restart executes once).
- **2. Rollback rewound the revision (High).** Rollback now persists the
  previous configuration with a FRESH revision (`max(prev, next) + 1`, never a
  rewind) and drops cached `tests`/`currentIp`, in both the background owner
  and the dev fallback — the failed route may have been installed briefly, so
  the interval stays visible to acceptance. The reproduction (B installs, the
  post-apply ownership query fails, rollback to A, then an A test with the old
  revision) now yields `stale-route` instead of `ok:true`. Regression:
  `owner.test.ts` "rollback carries a fresh revision and drops cached
  results".
- **3. 60s timer renewed a live request's auth budget (Medium).** The renewal
  timer is removed entirely: exhausted attempt markers are retained until
  completion/error events (the normal cleanup path), with a 1000-entry LRU
  bound for memory hygiene. A challenge arriving 60s+ later for the same live
  request is still over budget and gets `{}`. Worker restarts reset the bound
  (documented limit: in-flight-at-restart requests get a fresh budget).
  Regression: `owner.test.ts` fake-timer case (creds, advance 60001ms, `{}`).

### Remaining limits (not confirmed)

- No live proxy-traffic handshake or real credential exchange E2E.
- No real two-window (popup + options) race E2E; cross-context serialization
  is covered by owner-queue/dedup unit tests, not a live concurrency run.
- Rollback-write/commit failure still cannot guarantee storage/browser
  agreement (reported as `storage-failed`, flagged, not silently claimed).
- In-memory auth-budget markers are lost on worker restart (fresh budget for
  requests in flight during the restart); the persisted replay record covers
  mutations only.
- A manual user retry after an uncertain-completion error uses a NEW opId, so
  retrying a possibly-committed non-idempotent import can still duplicate —
  the user is told to check refreshed state first.
- Environment notes: `npm test`/`npm run lint` shims report permission denied
  in this checkout; equivalents were run directly (`node
  node_modules/vitest/vitest.mjs run`, `node node_modules/oxlint/bin/oxlint`,
  `node node_modules/typescript/bin/tsc -b`, `node
  node_modules/vite/bin/vite.js build`).

## Follow-up — 2026-10-05 (third pass: independent-review findings)

All five findings from the independent follow-up review are addressed below.
Verified with `tsc`, the Vitest suite (11 files / 82 tests, including the
three formerly-failing independent regression tests, which now pass), `oxlint`
(0 errors) and `vite build`, plus an isolated Edge smoke load (fresh
`--user-data-dir`, no personal settings changed). No live proxy-traffic or
two-window Edge E2E was performed. No "fully bug-free" claim is made.

### Fixed (verified by tests/build)

- **1. Single owner bypassed on messaging errors (High).** `dispatchOp` no
  longer replays mutations locally when messaging exists: any missing/failed
  background response refreshes state and throws `BackgroundUnreachableError`.
  (Original third-pass text described one same-opId auto-retry; that retry was
  removed in the fourth pass — see above — because in-memory dedup does not
  survive worker restarts.) Every mutation carries an `opId`; the background
  deduplicates by it (settled-result cache plus in-flight promise join,
  bounded at 100 entries / 5-min TTL, plus the persisted replay record added
  in the fourth pass), so a lost response followed by a same-opId retry can
  never duplicate an import or move a rule twice within one worker lifetime.
  The dev-mode local path (no `chrome.runtime` messaging only) is serialized
  as one unit via a local op queue. Regression: `ProxyService.rollback.test.ts` (transport
  failure rejects with no local write) and `src/background/owner.test.ts`
  (lost-response retry, simultaneous same-opId dedup, simultaneous distinct
  ops through the real `onMessage` handler).
- **2. Test verification accepted invalid/stale results (High).** Added
  `routingRevision` (`SCHEMA_VERSION` 2 → 3, migration preserves/zeroes it)
  bumped by every routing/credential mutation, and `StoredTest.rev`. Results
  are recorded only through atomic background acceptance (`acceptTest` /
  `acceptCurrentIp` ops): revision match + `resolveTargetForHost(...,
  'api.ipify.org')` match + ownership (`ours` whenever routing is intended,
  via the shared `expectsOwnership` helper) are checked inside the owner's
  exclusive queue, so intervening options edits, change-away-and-back
  (A → B → A), credential edits, and post-check/​pre-save races are discarded
  with `RouteStaleError` and no write. The dead `controlHeld` branch is gone;
  `checkCurrent` uses the same atomic path. Regression: `owner.test.ts`
  (intervening edit, A → B → A, lapsed ownership, rerouted check host) and
  `RoutingOps.test.ts` (revision bumps, validators).
- **3. Deleted rule target broke default-proxy auth (Medium).** The background
  auth guard now uses the same resolved-target semantics as PAC routing
  (`resolveTargetForHost`, including missing-target fallback and built-in
  bypasses) instead of comparing against the deleted target id, so the default
  proxy's credentials are served when the PAC falls back to it. The formerly
  failing independent test now passes; also covered in `owner.test.ts`.
- **4. Retry cleanup listeners misregistered (Medium).** `onCompleted` /
  `onErrorOccurred` are now registered with typed calls and the required
  `{ urls: ['<all_urls>'] }` filter (no casts), and the 60s fallback timer is
  armed only on the first attempt so a live request's budget is never renewed.
  The formerly failing independent registration test now passes; also covered
  in `owner.test.ts`.
- **5. Storage failures left requests unanswered (Medium).** `handleMutate`
  wraps the entire operation (initial read, initial write, routing,
  rollback) so every failure yields a structured `{ ok: false }` response,
  and the `onMessage` listener answers on both fulfillment and rejection.
  Regression: `owner.test.ts` (read failure, initial-write failure,
  rollback-write failure through the real listener — all answered).

### Test coverage note (acknowledged)

`ProxyService.rollback.test.ts` now covers the dev-mode fallback plus the

## Follow-up — 2026-10-05 (second pass)

Status per finding below. Fixes were verified with `tsc`, the Vitest suite
(10 files / 60 tests), `oxlint` (0 errors) and `vite build`; plus an isolated
Edge smoke load (fresh `--user-data-dir`, no personal settings changed). No
live proxy-traffic E2E was run (see limits). No "fully bug-free" claim is made.

### Fixed (verified by tests/build)

- **Stored routing vs actual browser routing.** `ProxyService.dispatchOp` +
  background `onlyproxy:mutate` owner now snapshot, persist, apply, verify
  ownership post-apply, and roll back storage (plus best-effort re-apply of the
  previous route) on any failure. `applyProfile` no longer falls back to null;
  `applyDirect` surfaces clear() failures instead of recording false Direct.
  Regression: `src/services/ProxyService.rollback.test.ts` (rejected apply,
  failed clear, edit rollback, post-apply ownership loss).
- **Updates are serialized.** `StorageService` has an in-context write queue,
  and all mutations go through the background single owner via delta ops
  (`activate/upsert/delete/addMany/replace/ruleAdd/ruleDelete/rulePatch/ruleMove/
  rulesEnabled/favorite/settings/saveTest/saveCurrentIp`) — views never submit
  stale whole lists. Regression: concurrent-update test in
  `ProxyService.rollback.test.ts`; rule delta ops in `RoutingOps.test.ts`.
- **Active profile / rule-target edits, deletes, replace imports.** Popup and
  options now use `upsertProfile/deleteProfile/addProfiles/replaceAll` and rule
  delta ops; every path re-applies routing with rollback and surfaces errors
  (popup/options error states, SiteRulesSection apply error). Replace import
  preserves the active profile when still present, else returns to default.
- **Proxy auth selects the wrong account.** `selectAuthCandidate`
  (`src/services/RoutingOps.ts`) + background handler: HTTP/HTTPS only, only
  active-or-enabled-rule-target profiles, request-URL rule preference for
  same-endpoint ties, ownership check (`controlled_by_this_extension`), Direct
  rules never leak creds, one answer per `requestId` with completed/error
  cleanup. Regression: `src/background/auth.routing.test.ts` (tie preference,
  SOCKS excluded, inactive excluded, retry bound, external ownership, rule
  routing) and `RoutingOps.test.ts`.
- **Rename to OnlyProxy.** User-visible branding is now OnlyProxy
  (popup/options/welcome titles, locale `extensionName`, error strings, README,
  STORE_RELEASE, CERTIFICATION_NOTES, PRIVACY_POLICY, `package.json` name,
  `onlyproxy-<version>.zip`). Historical `AUDIT.md` header intentionally kept.
  Build output verified (`dist/index.html`, locale).
- **Test verifies the wrong route.** `testProfile` now refuses while another
  op runs, blocks switching for its duration, rejects when site rules would
  route `api.ipify.org` elsewhere, verifies active/config/rules/ownership and
  `resolveTargetForHost(post, 'api.ipify.org')` after the fetch, and discards
  unverified results (`cause: 'config'`). Routing mutations invalidate
  `currentIp` and affected/all tests via `computeNextState`.
- **"Direct — no proxy" claim.** Behavior unchanged (`clear()` still restores
  the browser default/system connection). All user copy now says Direct
  Connection = browser default / no extension proxy (popup, welcome, options
  delete warnings, README, certification notes). No `direct` proxy mode was
  introduced.

- No real two-window (popup + options) race E2E; serialization is covered by

- Edge check was a smoke load only (isolated profile, `dist` loads, background

## Outstanding findings

### High: stored routing and actual browser routing diverge

- `src/services/ProxyService.ts`, `applyProfile`: if A is active and applying B
  is rejected, the stored selection becomes null instead of reverting to A.
- `applyDirect`: a failed clear is swallowed while null is saved. The UI can
  claim Direct while the old proxy remains configured. Both failure paths were
  reproduced with mocked browser settings APIs against the actual service.
- `src/popup/Popup.tsx`, `saveProfile`, and `src/options/Options.tsx`,
  `persistProfiles`: editing a profile does not reapply its active routing.
  Editing/deleting a site-rule target also leaves the installed PAC stale.
- `src/options/SiteRulesSection.tsx`, `persist`: rules are committed before
  applying them, and rejection is swallowed. Ownership checks cannot detect a
  stale PAC still owned by this same extension.

Required change: one background-owned operation for profile/rule mutations and
routing application, with explicit failure/rollback behavior, fresh snapshots,
and errors surfaced to callers. Apply the same operation to delete and replace
imports. Simply changing the rollback to the previous ID is insufficient when
that profile has already been deleted or another mutation is in flight.

### High: updates are not serialized

`src/storage/StorageService.ts`, `update`, independently reads, copies and writes
the entire state. Two concurrent preference updates were reproduced losing one
change, even within one JavaScript context. Popup/options also maintain separate
caches, and several profile changes use arrays captured by a previous render.
Storage change notifications do not provide transactional mutual exclusion.

Required change: serialize mutations through a single background owner and
operate on its fresh state; do not submit entire stale profile lists from views.
This belongs with the routing change above.

### High: proxy authentication selects the wrong account

`src/background/background.ts`, `getChallengeCredentials`, chooses the first
stored host/port match, including inactive profiles and SOCKS profiles. With A
and B on the same endpoint and B selected, the handler was reproduced returning
A's username. Stored credentials may also be supplied while routing is owned
outside this extension. Invalid credentials are retried without an extension
retry guard.

Required change: resolve the intended active/rule profile for the request,
verify routing ownership and HTTP/HTTPS applicability, define behavior for
same-endpoint account ambiguity, and bound retries per request with cleanup.
See the [official authentication event documentation](https://developer.chrome.com/docs/extensions/reference/api/webRequest#event-onAuthRequired).

### Medium: a successful test can verify the wrong route

`src/popup/Popup.tsx`, `testProfile`, labels the result of a request to
api.ipify.org as a profile test. A site rule for that domain can send the request
Direct or through another profile. The currently selected profile skips
reapplication even when another extension has taken control. Switching while
the request runs is also allowed. Thus a successful IP fetch does not establish
that the named proxy works.

Required change: define tests as current-route checks or verify and hold the
tested route for their duration; never attach a result to an unverified profile.
Invalidate cached current-IP/profile-test results when their configuration changes.

### Medium: “Direct — no proxy” does not describe clear()

Outside PAC mode the code uses settings.clear(), intentionally restoring the
browser's previous/system configuration. If that configuration has a proxy,
the UI's “no proxy” claim is false. Either label this as the default/system
connection or deliberately implement direct mode, consistently in the UI/docs.
See the [official proxy mode documentation](https://developer.chrome.com/docs/extensions/reference/api/proxy#proxy-modes).

## Isolated fixes applied

- Declare the background worker as an ES module. The existing dist/background.js
  starts with an import, incompatible with the previous classic-worker manifest.
  This follows the [worker import requirement](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/basics#import-scripts).
- Set PAC mandatory in both application paths, preventing invalid PAC scripts
  from silently falling back to Direct. This does not implement a general kill
  switch. See [PacScript.mandatory](https://developer.chrome.com/docs/extensions/reference/api/proxy#type-PacScript).
- Complete asynchronous origin-server authentication callbacks without sending
  proxy credentials.
- Persist migration data before removing legacy keys; keep failed writes out
  of the cache; do not replace a failed Chrome storage read with empty state.
- Copy rule objects when constructing a storage draft.
- Validate real IPv6 structure, rejecting malformed colon sequences.
- Reject explicitly unsupported JSON-import protocols instead of silently
  converting them to HTTP; retain HTTP default for absent protocol fields.
- Avoid displaying favorite search results twice; avoid the green routing
  indicator when the rule master switch is off.
- Remount the settings edit form when selecting a different profile, preventing
  values from the previous profile from being saved over the next one.
