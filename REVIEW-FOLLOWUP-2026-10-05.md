# Independent follow-up review

Verdict: improvements confirmed, but not approved for release yet. OnlyProxy
branding was explicitly authorized and is not a finding. Application source
was not changed during this review; the build was regenerated by validation.

## Validation independently rerun

- Existing Vitest suite: 10 files, 60 tests passed.
- TypeScript build: passed.
- Oxlint: no errors; warnings remain (not treated as release blockers here).
- Vite production build: passed.
- Three additional targeted regression tests: all failed, confirming gaps below.
  Temporary test source preserved at `/tmp/onlyproxy-independent-review.test.ts`.
  It was removed from src after execution, leaving the existing suite intact.
- No live proxy handshake or two-window Edge E2E was performed in this review.

## 1. High: the single owner is bypassed on messaging errors

Locations: `src/services/ProxyService.ts:34`, `dispatchOp` local fallback.

Every missing/failed response from background is converted to null, then the
caller writes and applies the operation itself. A closed message channel does
not establish that the background did not execute the operation. Local replay
can duplicate an import or move a rule twice; parallel windows again have
independent mutation owners. The fallback read/compute/write sequence is not
serialized as a unit either.

Independent test: make sendMessage reject, call patchSettings, require an error
and no local write. Actual result: success via the local fallback.

Fix: allow local execution only in explicit browser-development mode without
extension APIs. In an installed extension, report transport failure and refresh
state, or use operation IDs and background-side deduplication for retries.
Test successful background execution followed by a lost response, as well as
simultaneous requests through the actual background message handler.

## 2. High: profile verification still accepts invalid/stale results

Location: `src/popup/Popup.tsx:223-260`; `RoutingOps` saveTest/saveCurrentIp.

`controlHeld` is calculated but does not gate success. With unchanged stored
state, postControl='controllable' and r.ok=true, the code saves a successful
profile test even though the extension no longer owns the route.

The lock is also popup-local, not shared with options. Comparing endpoint/rules
before and after does not detect A -> B -> A while a request is in flight, and
the snapshot excludes username/password changes. Finally a routing mutation can
occur between the post-check and saveTest: the background accepts that stale
result unconditionally. checkCurrent has no route consistency check at all.

Fix: attach a routing revision to tests, increment it for every routing/auth
change, and accept results atomically in the background only for the same
revision and valid ownership. Discard success whenever ownership is not ours
in extension mode. Test intervening options edits and change-away-and-back.

This finding is from direct control-flow inspection; the popup was not mounted
in an E2E test during this review.

## 3. Medium: deleting a rule target breaks default-proxy authentication

Location: `src/background/background.ts:371-378`.

The PAC falls back to the global profile when a rule target is missing. Auth
selection can return that global profile, but the extra guard rejects it
because the deleted target cannot be found. The network goes to the correct
proxy but the handler withholds its credentials.

Independent test: global authenticated A, enabled rule for example.com pointing
to a deleted profile, challenge from A. Expected A's credentials; actual {}.

Fix: use the same resolved target semantics for PAC, validation and auth guards,
including missing-target fallback and built-in bypasses.

## 4. Medium: retry cleanup listeners are not registered correctly

Location: `src/background/background.ts:419-420`.

Both webRequest addListener calls omit the required filter. The casts suppress
type checking, and the catch hides registration failure. The completion/error
cleanup does not work in the real API; only the timer remains, which also resets
the attempt budget for a still-running request after 60 seconds.

Independent test verified that listener registration supplies only the callback,
not the required filter. The official contract requires it:
[webRequest listener registration](https://developer.chrome.com/docs/extensions/reference/api/webRequest#registering-event-listeners).

Fix: use typed API calls with `{ urls: ['<all_urls>'] }` and a retry lifetime that
does not renew a live request's budget. Test using strict API doubles.

## 5. Medium: storage failures leave mutation requests unanswered

Locations: `src/background/background.ts`, handleMutate initial read/write;
onMessage line 530.

The initial read and set occur outside the routing try/catch. A storage rejection
rejects handleMutate; the message listener has only a fulfillment handler and
has already returned true. No error response is sent, leaving the caller pending
until the channel closes (which also triggers the unsafe fallback in finding 1).

Fix: catch errors around the entire message operation and always send a
structured failure response. Test storage read failure, initial write failure
and rollback-write failure through the actual onMessage listener, not only the
local ProxyService fallback.

## Test coverage observation

ProxyService.rollback.test.ts deliberately makes sendMessage fail, so its
rollback tests exercise the local fallback, not handleMutate in background.
Its concurrency test calls StorageService.update directly after warming the
cache. These passing tests do not validate the production owner or cross-window
serialization. The next pass should add tests at that production boundary.
